Aegisub retains its ASS editing, audio timing and Lua automation workflow. The YouTube feature adds conversion, compatibility diagnostics, an approximation derived from the generated YTT, and an optional real YouTube player check.

**Install and open on macOS.** The macOS package targets Apple Silicon ARM64 and macOS 26 or later; the macOS minimum is inherited from the base native build. End users need neither Rosetta nor a developer .NET SDK/runtime. Google Chrome must be installed separately for the real-player feature; it is not bundled.

Extract the delivered ZIP and open `Aegisub YouTube.app`. Keep the accompanying `Samples`, guide, audit and checksum files. The package is **ad-hoc signed, not Developer ID signed or notarized**: signing does not guarantee that a downloaded app passes Gatekeeper.

If you trust the distribution and choose to allow it, first attempt to open it, then use **System Settings → Privacy & Security → Security → Open → Open Anyway**, and authenticate. The exception button is available for about an hour after the attempt. Do not disable Gatekeeper systemwide. See [Apple’s instructions](https://support.apple.com/guide/mac-help/open-a-mac-app-from-an-unknown-developer-mh40616/mac).

**Use the editor.**

1. Open your ASS and video, or the provided `Samples/한글 샘플.ass` with your own video/dummy video at 1280×720. `Samples/한글 샘플.srt` demonstrates plain-text compatibility; no video is bundled.
2. Open **File → YouTube** (`파일 → YouTube`). The dialog contains conversion settings, selected-row effects and compatibility diagnostics.
3. Let conversion finish. Toggle `영상 화면에서 YouTube 변환 결과 보기 (시각적 근사치)` to compare source ASS with the visual approximation produced from the actual generated YTT. Both use Aegisub’s existing playback/seek clock.
4. Use `영상·자막 편집` to return to editing; conversion continues in the background. Reopen File → YouTube to review status, or use `다시 변환` / `변환 취소`.
5. Double-click a diagnostic to select its subtitle row and seek to its start. Resolve relevant warnings before choosing `내보내기 묶음…`.

Style conversion settings are stored in the ASS `[Script Info]` entry `Aegisub Youtube Options`; save the ASS to retain them. Changes participate in Undo, and the preview/export use the same settings snapshot. Keep the `Default` style stable: converter font scaling is relative to its font size, with first-style fallback when `Default` is absent.

**PlayRes and caption size.** 640×360 is not a universal fix. For subtitles authored at 1920×1080, changing only PlayRes to 640×360 leaves existing pixel tags such as `\pos(960,980)` outside the new coordinate space. The converter clamps this example to YTT `(ah,av)=(100,100)`.

A full resample divides every pixel value by three, including style font sizes, explicit positions, margins, outline and shadow. With the default output profile (scale 1, zero X/Y offsets), `\pos(960,980)` becomes `\pos(320,326.667)` and retains YTT `(50,92)`: both coordinates and PlayRes shrink together. Scaling all styles from 60 to 20 also preserves the font/default-style ratio (`60/60 = 20/20 = 1`) and YTT pen `sz=100`. Full resampling therefore preserves these normalized coordinates and font ratios; it does not itself shrink the YTT captions or establish correct mobile layout. Check the target player/device separately; the limited device observations below do not establish compatibility across all environments.

Selected-row effects modify ASS and support Undo. Fade/transform times are milliseconds relative to the event start; ASS karaoke `\k` durations are **10 ms units** (500 ms = `\k50`). The effect UI accepts milliseconds and converts karaoke units. Color controls use RRGGBB; raw ASS color tags follow ASS syntax.

Output-profile scale is a multiplier; X/Y offsets use ASS PlayRes pixels and affect explicit positions. The mobile profile simplifies styling and removes drawing-mode content while retaining non-drawing text. The original ASS is retained. **Device observations are limited to the cases below; this profile is not a mobile-rendering certification.**

**Device observations (user report, 2026-09-15).** The user confirmed that all three rows remain separate in Android fullscreen playback. The remaining differences were the black background and font appearance, which were accepted as platform limitations for this case. On iPhone, the user reported that the last row still flickered in the earlier position-corrected version.

The second, single-outline variant reduced four stacked effect copies to one, taking YTT `<p>` events from 7,932 to 1,983 while preserving text, colors and timing. The user still observed iPhone flicker in this single-outline version, so reducing the stacked effect copies alone did not resolve this case.

**The third variant is the selected final version.** It puts the three rows in one multiline YTT caption block, has been uploaded, and desktop playback confirmed all three visible rows. **After reopening on iPhone, the user confirmed that flicker was gone at 28–31 seconds.** This result is limited to the user's tested device and that segment; it does not guarantee the same result across all iOS devices or playback conditions.

**Background and font differences across players.** The [pinned upstream README's Limitations](https://github.com/arcusmaximus/YTSubConverter/blob/b186a40bc21e58a8c9651cf616cbb5e80425dfc6/README.md#limitations) describes mobile apps imposing black caption boxes regardless of the requested background color or transparency. The [related YttDocument comment](https://github.com/arcusmaximus/YTSubConverter/blob/b186a40bc21e58a8c9651cf616cbb5e80425dfc6/YTSubConverter.Shared/Formats/YttDocument.cs#L539-L546) describes that background restriction and explains why its Android dark-text workaround does not work the same way on iOS, which handles text transparency differently. Desktop, Android and iOS appearance need not match; neither setting PlayRes to 640×360 nor fully resampling guarantees removal of black backgrounds or font differences.

**Export and import.** Export can include `result.ytt`, `source.ass` (with conversion settings), `compatible.srt` and the conversion manifest. SRT loses styling, positioning and effects. Keep ASS as the editable master; YTT is a converted output.

`YTT → 편집용 ASS` imports YTT/SRV3 to a new ASS path, leaving the current document intact; open that file afterward through File → Open Subtitles. Expanded effects cannot necessarily be reconstructed into the original authoring tags.

**Check the real YouTube player.**

1. Install Google Chrome on macOS, or Chrome/Microsoft Edge on Windows, then enter a public watch URL such as `https://www.youtube.com/watch?v=RKK7wGAYP6k` and the language code of an existing manual caption track.
2. After conversion is current, choose `실제 플레이어 시작`. In the dedicated browser window, enable that exact language’s CC track. Automatic captions and translated tracks are excluded; the feature does not create a missing track.
3. After editing and reconversion, switch CC **off, then on** to request the new local captions. A matching successful response ACK updates the application status; inspect the player’s pixels as well.
4. Choose `플레이어 종료`. The helper stops its own browser process tree and deletes its unique temporary profile.

On Windows, [browser discovery](../tools/youtube/PlayerPreview.cs) checks Chrome in Program Files, Program Files (x86) and Local AppData, then Edge in those same locations; it selects the first existing executable. On macOS it defaults to `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`. To use another installation, set `AEGISUB_YOUTUBE_CHROME` to the full browser executable path before launching Aegisub. This override takes precedence on both platforms. For example, in PowerShell, replace the path as needed and launch Aegisub from that same shell:

```powershell
$env:AEGISUB_YOUTUBE_CHROME = 'C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe'
& 'C:\path\to\Aegisub\aegisub.exe'
```

CC off/on updates and renewed ACK status were observed through the actual app at **2026-09-14 17:02:58 KST**. This is desktop evidence, not mobile coverage. A waiting status can mean no matching manual-language request has occurred.

The helper uses loopback Chrome DevTools Protocol (CDP), intercepting only `https://www.youtube.com/api/timedtext*` and fulfilling matching video/language requests with local YTT bytes. It uses no proxy, certificate installation, TLS bypass or subtitle upload. Normal YouTube video playback still uses the network.

A fulfilled response is confirmed only after its command-ID-correlated successful CDP ACK. `status.txt` starts with `SHA256 <hash>` for the exact fulfilled bytes; the native UI accepts confirmation only for its current ready revision and matching YTT hash. This establishes response identity, not successful caption layout or pixel equivalence. Session `protocol.log` supports investigation.

The converter remains pinned to [arcusmaximus/YTSubConverter b186a40](https://github.com/arcusmaximus/YTSubConverter/tree/b186a40bc21e58a8c9651cf616cbb5e80425dfc6). The vendored [full fork patch](../tools/youtube/patches/independent-justification.patch) includes both `27472674e6217f4f3407bb855476529e6dd5412e` and `c460cca9f5b37aa0e98e460007f7379df5732d05` from [DO0OG’s independent-justification branch](https://github.com/DO0OG/YTSubConverter/compare/b186a40bc21e58a8c9651cf616cbb5e80425dfc6...c460cca9f5b37aa0e98e460007f7379df5732d05). MIT notices are retained in the [vendored license](../tools/youtube/patches/YTSubConverter-LICENSE); this does not relicense Aegisub as a whole.

The patch preserves independent YTT `ap` (anchor) and `ju` (text justification) through reading, cloning and writing, including distinct style-pool entries. Our [ASS bridge patch](../tools/youtube/patches/ass-justification.patch) and [tag handler](../tools/youtube/upstream-support/AssJustificationTagHandler.cs) add **custom** `\ytju0` (left), `\ytju1` (right), `\ytju2` (center), keeping `\an` as the anchor. This extension is not standard ASS support in other renderers.

**Independent justification is preserved in editable ASS/YTT data, but its visual rendering is incomplete.** The existing ASS visualizer still aligns from the anchor, so independently justified multiline text can differ. The manifest emits `YTJU_VISUAL_ALIGNMENT` in `visualDiagnostics` and `visualIndependentAlignmentPreserved=false` for mismatches; import emits JSON warnings to stderr, and native diagnostics warn on `ytju`. Verify `result.ytt` in the real player. A true alignment flag only means this mismatch was absent, not that all visuals are exact.

The [full package script](../tools/youtube-package.sh) builds the native core/bundle, helper and AppKit library, signs and audits ARM64 dependencies, smoke-tests the helper without DOTNET_ROOT/developer PATH, then creates a timestamped delivery folder, ZIP and SHA-256 file under `artifacts/`. `--reuse-core` skips the native rebuild; it still rebuilds the helper and requires the existing bundle and audit environment.

The [helper build script](../tools/youtube-build.sh) verifies pinned downloads, applies patches to a private source copy under `tools/youtube/obj`, and overlays the official Microsoft **10.0.9 osx-arm64 runtime** plus hostfxr. This fixes the Homebrew runtime’s external Brotli dependency in the published helper. It includes converter/.NET notices and re-signs adjusted libraries. Do not substitute an arbitrary Homebrew runtime copy. No npm is required.

The [Ruby regression runner](../tools/youtube-test.rb) covers pinned golden fixtures with their `StyleOptions.xml`, tag parsing/timing, all 27 anchor/justification combinations and coordinate round trips, alignment diagnostics, source retention and mobile drawing removal. Golden comparison removes only a leading UTF-8 BOM; XML reformatting or silently omitting style options would invalidate the oracle.

**Bundled helper CLI on macOS.** Replace the package placeholder with your extracted delivery directory; outputs must use new paths. The Korean fixtures are also in [tests/youtube-fixtures](../tests/youtube-fixtures).

```bash
PACKAGE="/path/to/extracted/delivery"
APP="$PACKAGE/Aegisub YouTube.app"
HELPER="$APP/Contents/MacOS/youtube/aegisub-youtube"
OUT="$(mktemp -d)"
"$HELPER" --help
"$HELPER" preview "$PACKAGE/Samples/한글 샘플.ass" "$OUT/preview"
"$HELPER" import "$OUT/preview/result.ytt" "$OUT/imported.ass"
# Optional explicit converter settings XML:
# "$HELPER" preview INPUT.ass NEW_OUTPUT_DIRECTORY STYLE_OPTIONS.xml
# Optional real player; en must match an existing manual track:
"$HELPER" player 'https://www.youtube.com/watch?v=RKK7wGAYP6k' \
  "$OUT/preview/result.ytt" en "$OUT/player"
# From a second terminal, using the same OUT value: touch "$OUT/player/stop"
```

The CLI preview does not automatically extract GUI settings from ASS metadata: pass `STYLE_OPTIONS.xml` explicitly when reproducing those settings. Expected preview files are `result.ytt`, `preview.visual.ass`, `compatible.srt`, `source.ass` and `manifest.json`.
